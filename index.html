eax: add Wycheproof test vectors RustCrypto/AEADs #894 · Test coverage
Problem
The eax crate's only failing-vector file was empty, so no test checked that a wrong tag is rejected: with the tag comparison forced to succeed, every test still passed. AES-192 and AES-256 had no test vectors at all.
Background
Validation test vectors (Wycheproof), the same approach as known-answer testing in cryptographic module validation (KCMVP): run the published vectors and check that a forged tag is refused.
How it was found
Running all Wycheproof AES-CCM and AES-EAX vectors against the crates (672 cases, no mismatch) and then checking which of them the crate's own tests cover; a mutant with the tag check disabled passed the existing tests.
Fix
186 Wycheproof cases (105 valid, 81 invalid) for AES-128, AES-192 and AES-256 through the aead test macros. With the tag check disabled, the three new failure tests fail.

Problem

Problem

pkcs5: return an error from Salt::new for salts longer than MAX_LEN RustCrypto/formats #2502 · Bug fix
Problem
pkcs5::pbes2::Salt::new is documented to return an error for a salt longer than 32 bytes, but the length check was dropped in #2295. A 33-byte salt passed to Salt::new, Pbkdf2Params::hmac_sha256 or ScryptParams::from_params_and_salt panicked with an index out of bounds instead. Background
PKCS #5 PBES2 (RFC 8018): PBKDF2 and scrypt parameters carry the salt as an OCTET STRING. This crate stores it in a fixed 32-byte buffer so it works without an allocator.

Fuzzing the formats decoders and constructors with libFuzzer. The decoder checks the length; the caller-supplied constructor did not. git log -p traced the missing check to #2295.
Fix
Restore the length check. New tests cover a 33-byte salt (fails without the fix) and a 32-byte salt; pkcs5 tests, clippy and rustfmt pass.

der: reject malformed binary REAL values instead of panicking RustCrypto/formats #2501 · Bug fix
Problem
After #2483 fixed truncated content, the der crate's ASN.1 REAL (f64) decoder still panicked on a mantissa longer than eight octets, and on a zero mantissa or an out-of-range exponent in debug builds. In release builds the last two decoded to NaN and to an unrelated value (exponent 0x7fff gave 0.5).
Background
X.690 binary REAL encoding: sign, base, scaling factor F, exponent octets, then mantissa octets; zero has no contents octets (8.5.2). An IEEE-754 double needs the exponent within -1023..=1023 for this decoder's mapping.
How it was found
Reading the decoder after #2483 for the remaining unchecked arithmetic, then reproducing each input on master and on der 0.8.3 in debug and release builds.
Fix
Return a value error for each case. A new test covers the inputs and fails when any one of the three checks is removed; der tests pass (120).

tls_crypt: Wipe the tls-crypt-v2 client key copies OpenVPN/openvpn Gerrit 2079 · Hardening
Problem
tls_crypt_v2_init_client_key() left a stack copy of the client key at every client start, and tls_crypt_v2_write_client_key_file() freed the key data and the wrapped key buffer without clearing them.
Background
Zeroisation (ISO/IEC 19790, FIPS 140-3, KCMVP), matched to the project's own precedents: crypto_read_openvpn_key() already clears the same stack copy and do_close_free_key_schedule() the same kind of buffer.

A stack residue measurement and a freed-block scan with a marked test client key.
Fix
secure_memzero() on the stack copies and buf_clear() before free_buf(). Together with Gerrit 2078 the stack copies go from 2 to 0, and the two freed blocks from key generation disappear.

Approved (Code-Review +2) by Steffan Karger.

Problem
crypto_pem_decode() decodes the tls-crypt-v2 client and server keys and the auth-token key, and freed the decoded key bytes with OPENSSL_free(), so they stayed in freed memory.
Background
Zeroisation (ISO/IEC 19790, FIPS 140-3, KCMVP) in a project that builds with both OpenSSL and LibreSSL, so the clearing call has to exist in both.

Scanning the blocks freed during the tls-crypt unit tests for the test key.
Fix
OPENSSL_cleanse() and then OPENSSL_free(). The first patch set used OPENSSL_clear_free(), which LibreSSL does not have; the second builds with --enable-werror against LibreSSL 4.3.4 and OpenSSL 3.5.9, and the freed blocks holding key bytes go from 2 to 0.

Approved by Steffan Karger, then Gert Doering found the LibreSSL build failure and suggested the two-line form; the second patch set does exactly that and waits for another look.

ssl: Wipe the key source material in key_state_free() OpenVPN/openvpn Gerrit 2075 · Hardening
Problem
ks->key_src holds the pre-master secret and the random values the peers exchange in key method 2. Background

Fix

Problem
In extract-only mode, HKDF and TLS13-KDF output exactly one digest. The default provider refuses any other output length up front; pkcs11-provider passed the requested length to the token and checked it only after the token had returned the derived value.
Background
HKDF (RFC 5869) extract step, the PKCS#11 HKDF mechanism and OpenSSL's KDF provider API: the provider has to match the default provider's length rules before calling the token.

Running extract-only HKDF with several output lengths through both the default provider and pkcs11-provider and comparing the results.
Fix
Check the length before deriving and raise the default provider's error. The new hkdfextract test covers HKDF and TLS13-KDF with SHA-256 and SHA-512, and fails with the check reverted.

Check raw RSA sign data against the modulus, not the buffer size openssl-projects/pkcs11-provider #815 · Bug fix
Problem
Raw RSA signing (RSA_NO_PADDING) on a token key failed whenever the output buffer was larger than the modulus, although the input was correct; the default provider signs the same input into the same buffer and returns the modulus size.
Background
RSA and OpenSSL provider API: EVP_PKEY_sign() takes the buffer size in *siglen, and raw RSA requires the input to be exactly as long as the modulus (CKM_RSA_X_509 in PKCS#11).
How it was found
The same buffer-size sweep, comparing pkcs11-provider with OpenSSL's default provider: buffers of 257, 512 and 8448 bytes failed on the token and succeeded on the default provider.
Fix
Compare the input length with the key's modulus size instead of the caller's buffer size. The new rsaraw test checks both providers, recovers the data from the token signature, and still refuses input shorter than the modulus.

Cancel the signing operation after CKR_BUFFER_TOO_SMALL openssl-projects/pkcs11-provider #814 · Bug fix
Problem
One signature into a buffer that was too small left the signing operation active on a pooled PKCS#11 session. Every later signature that picked up that session failed with CKR_OPERATION_ACTIVE: with NSS softokn, one 255-byte buffer for a 2048-bit RSA key broke all RSA, RSA-PSS, ECDSA and DigestSign signatures for the rest of the process.
Background
PKCS#11 session semantics: C_Sign() returning CKR_BUFFER_TOO_SMALL keeps the operation active so the caller can retry with a larger buffer, so a provider that pools sessions has to end the operation before handing the session back.
How it was found
A buffer-size sweep: every signature, derivation and decryption path of pkcs11-provider was run with buffers smaller and larger than needed, then followed by a normal call to see whether the session was still usable.
Fix
Move the existing cleanup for a hanging operation into a helper and call it on CKR_BUFFER_TOO_SMALL before the session is returned. The new sigbuf test fails without the change and passes with it.

Return only the ECDH secret into larger buffers openssl-projects/pkcs11-provider #813 · Bug fix
Problem
With a PKCS#11 token, EVP_PKEY_derive() asked the token for as many bytes as the caller's buffer instead of the size of the shared secret. NSS softokn returned the P-256 secret left-padded with zeros, so a 64-byte buffer got 32 zero bytes before the secret and the two sides of an ECDH exchange no longer agreed.
Background
PKCS#11 and HSM integration: an ECDH derivation (CKM_ECDH1_DERIVE with CKD_NULL) takes its output length from CKA_VALUE_LEN in the key template, while OpenSSL's EVP_PKEY_derive() treats the length as the buffer size and reports how many bytes it wrote.
How it was found
Differential testing: the same ECDH derivation through OpenSSL's default provider and through pkcs11-provider on an NSS softokn token, with output buffers of several sizes.
Fix
Cap the requested length at the key size. The new regression test then exposed an older leak: deriving twice on one context overwrote the copy of the peer's public point, which the Address Sanitizer job reported. That leak is fixed in the same pull request.
Review
The maintainer approved the change, then asked for the regression test to be restructured and for the Address Sanitizer failure to be fixed; both followed in new commits.

Return CKR_SIGNATURE_LEN_RANGE for a wrong-length EdDSA signature latchset/kryoptic #579 · Bug fix
Problem
C_VerifySignatureInit takes the signature to verify as an input, but for EdDSA it was handed straight to the signature context with no length check, so a wrong-length signature was only rejected later, when C_VerifySignature failed with CKR_FUNCTION_FAILED.
Background
PKCS#11 signals a signature whose length is wrong with CKR_SIGNATURE_LEN_RANGE. Kryoptic's ECDSA, RSA, ML-DSA, SLH-DSA, HMAC and CMAC already apply that check at init; EdDSA (64 bytes for Ed25519, 114 for Ed448) was the only mechanism missing it.
How it was found
Wycheproof ed25519/ed448 verification vectors carrying wrong-length signatures, run through the VerifySignature API: the mismatched lengths were accepted at init instead of being rejected.
Fix
Compare the supplied signature length against the expected output length before setting it on the context, mirroring the existing ECDSA check, and extend the EdDSA test to reject a wrong-length signature for both curves.

Problem
When C_DecryptUpdate was called two or more times with chunks longer than the 16-byte tag, the front of each later chunk was never decrypted. The output came out short and C_DecryptFinal rejected valid ciphertext with CKR_ENCRYPTED_DATA_INVALID.

AEAD streaming: in multi-part decryption the token cannot know which bytes are the Poly1305 tag until C_DecryptFinal, so it must hold back the last 16 bytes of every update and still decrypt everything in front of them.

Return CKR_PUBLIC_KEY_INVALID for an invalid ECDH peer point latchset/kryoptic #566 · Bug fix
Problem
CKM_ECDH1_DERIVE reported a peer public point that is not on the curve, has the wrong length or uses a bad compressed encoding as CKR_DEVICE_ERROR, so a caller could not tell a corrupted or hostile peer key from a fault in the token.
Background
PKCS#11 return-code rules: a public key that cannot be used is CKR_PUBLIC_KEY_INVALID, while CKR_DEVICE_ERROR means the token itself failed. An ECDH peer key comes from the other side of the key exchange, so it is untrusted input.
How it was found
Wycheproof ECDH vectors (P-256, P-384, P-521, X25519, X448; 2,834 cases) run through C_DeriveKey: every result matched, but 79 of the 82 invalid cases came back as CKR_DEVICE_ERROR.
Fix
Map a failed peer-key import to CKR_PUBLIC_KEY_INVALID. A new test case derives with an off-curve P-256 point and fails without the change.
Review
The maintainer asked for CKR_PUBLIC_KEY_INVALID instead of CKR_MECHANISM_PARAM_INVALID. Changed in a follow-up commit; the Wycheproof rerun gives CKR_PUBLIC_KEY_INVALID for all 79 invalid peer points.

Problem
The modular inverse routine freed its work buffer without clearing it. After mbedtls_mpi_inv_mod() the inverse stayed in freed heap memory, and after 2048-bit RSA key generation the private CRT coefficient QP did.
Background
Cryptographic module validation: critical security parameters must be zeroized when no longer needed (ISO/IEC 19790 and its Korean counterpart used in KCMVP), and RSA-CRT private keys include QP = q^-1 mod p.

mu: Accept a NULL offset in the TPMS_EMPTY marshalling functions tpm2-software/tpm2-tss #3198 · Bug fix
Problem
Tss2_MU_TPMS_EMPTY_Marshal() and Tss2_MU_TPMS_EMPTY_Unmarshal() read *offset for a debug log line without checking it. Every other function in the file accepts a NULL offset; these two read through a NULL pointer.
Background
tpm2-tss builds its marshalling (MU) functions from C macros, and each macro logs offset ? *offset : 0xffff. At the default log level LOG_DEBUG() is a plain function call, so its arguments are evaluated even when debug logging is off.
How it was found
Calling the MU functions with a NULL offset under UndefinedBehaviorSanitizer.
Fix
TPMS_MARSHAL_0 and TPMS_UNMARSHAL_0 log offset ? *offset : 0xffff like the other macros. A new unit test stops with the UBSan report when the fix is reverted; TPMS-marshal passes 12/12.
