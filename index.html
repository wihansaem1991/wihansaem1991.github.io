OpenSSL — Clear the PBKDF1 derived key in kdf_pbkdf1_derive_skey()Approved

openssl/openssl #33444 · submitted 2026-10-29 · Approved 2026-10-30 · master, 3.6, 4.0, 4.1
Problem
The derived key was imported as an EVP_SKEY and its temporary buffer freed with OPENSSL_free(), leaving the whole key in released heap memory.
Background
Key zeroisation as required by ISO/IEC 19790, the standard behind FIPS 140-3 and Korea's KCMVP validation: a derived key is secret material and has to be cleared before its memory is released. OpenSSL provides OPENSSL_clear_free() for exactly this.
How it was found
A measurement program that replaces OpenSSL's allocator and scans every freed block for key bytes: a 20-byte block holding the full key, freed at pbkdf1.c:318.
Fix
OPENSSL_clear_free() on both paths; test_kdf_pbkdf1_skey now watches freed blocks and fails if the change is reverted.
Review
Approved by two reviewers; triaged as a bug with FIPS relevance.
Evidence

pkcs11-provider — Return only the ECDH secret into larger buffersUpdated, awaiting re-review

openssl-projects/pkcs11-provider #813 · submitted 2026-10-30
Problem
With a PKCS#11 token, EVP_PKEY_derive() asked the token for as many bytes as the caller's buffer instead of the size of the shared secret. NSS softokn returned the P-256 secret left-padded with zeros, so a 64-byte buffer got 32 zero bytes before the secret and the two sides of an ECDH exchange no longer agreed.
Background
PKCS#11 and HSM integration: an ECDH derivation (CKM_ECDH1_DERIVE with CKD_NULL) takes its output length from CKA_VALUE_LEN in the key template, while OpenSSL's EVP_PKEY_derive() treats the length as the buffer size and reports how many bytes it wrote.
How it was found
Differential testing: the same ECDH derivation through OpenSSL's default provider and through pkcs11-provider on an NSS softokn token, with output buffers of several sizes.
Fix
Cap the requested length at the key size. The new regression test then exposed an older leak: deriving twice on one context overwrote the copy of the peer's public point, which the Address Sanitizer job reported. That leak is fixed in the same pull request.
Review
The maintainer approved the change, then asked for the regression test to be restructured and for the Address Sanitizer failure to be fixed; both followed in new commits.

Mbed TLS — Reject repeated X.509 extensions that have no parserAwaiting review

Mbed-TLS/mbedtls #11036 · submitted 2026-10-30
Problem
Mbed TLS rejected a certificate that repeated an extension it parses, but accepted one that repeated an extension it skips or hands to a callback.
Background
RFC 5280 section 4.2: a certificate must not include more than one instance of a particular extension. Applying that rule needs the DER layout of the extensions sequence, since skipped extensions are never decoded.
How it was found
Issue #4069, where a maintainer had proposed the approach. Test certificates were generated for the missing cases; two of them were wrongly accepted before the fix.
Fix
When an extension is skipped or passed to the callback, compare its OID with the extensions already read and reject a repeat; three new test cases (902/902 in test_suite_x509parse).

mitmproxy — Apply config file options before addons see --set confdirAwaiting review

mitmproxy/mitmproxy #8548 · submitted 2026-10-31
Problem
With --set confdir=..., mitmproxy loaded the CA from that directory before reading cert_passphrase from the directory's config.yaml. An encrypted CA key then failed to load and mitmproxy exited at startup (issue #6014, open since 2023).
Background
TLS interception: mitmproxy signs certificates on the fly with its own CA, so the CA private key has to load at startup, and an encrypted PKCS#8 key needs its passphrase first. Its option manager notifies addons on every update, so the order of updates decides what an addon sees.
How it was found
Issue #6014 with the maintainer's diagnosis, and a stalled pull request from 2023 that had never been reviewed. Reproduced on Linux with an encrypted CA.
Fix
Work out the --set options and the config file on a copy of the options (a copy has no subscribers) and apply the result in one update; precedence is unchanged. A new test runs mitmdump with an encrypted CA and fails with the old order.

RustCrypto — ml-dsa: check Wycheproof verify vectors that have a contextAwaiting review

RustCrypto/signatures #1493 · submitted 2026-10-31
Problem
The ML-DSA Wycheproof verification test skipped every case with a context string, so deleting the check that rejects contexts longer than 255 bytes left all tests passing.
Background
FIPS 204: ML-DSA signing and verification reject a context string longer than 255 bytes. The C2SP Wycheproof vectors test exactly that with 7-, 255- and 256-byte contexts.
How it was found
Running the Wycheproof ML-DSA vectors against the crate, then mutation testing: removing the length check went unnoticed by every existing test.
Fix
Run the context cases through verify_with_context(). With the length check removed, the ML-DSA-44, -65 and -87 tests now fail.

OpenSSL — Clear type-specific private key DER before freeing itAwaiting CI approval

openssl/openssl #33426 · submitted 2026-10-28
Problem
key_to_type_specific_der_bio() freed the DER produced by the key's i2d function with OPENSSL_free(). For a private key that buffer holds the whole key, so every i2d_PrivateKey() or "type-specific" DER encoding of an RSA, EC, DSA or SM2 key left it in freed memory. The PEM path already cleared its copy.
Background
The zeroisation rule of ISO/IEC 19790 (FIPS 140-3, KCMVP) and how OpenSSL 3 encoders hand key material between i2d functions and BIOs.
How it was found
The freed-block measurement program, which swaps OpenSSL's allocator and looks for key bytes in every freed block, run over the key encoders.
Fix
OPENSSL_clear_free() for the encoded buffer. test_type_specific_der_cleanse encodes an RSA key both ways under a watching allocator and fails without the fix.

OpenSSL — Clear the EVP_ENCODE_CTX when freeing itAwaiting CI approval

openssl/openssl #33430 · submitted 2026-10-28
Problem
The base64 context keeps the last partial line of its input and was freed without clearing it. PEM_write_bio() encodes private key DER through such a context, so the last (length mod 48) bytes of the key stayed in freed memory: the end of iqmp for RSA, private key bytes for Ed448, ML-DSA and ML-KEM. Reading PEM left base64 text the same way.
Background
Zeroisation (ISO/IEC 19790, FIPS 140-3, KCMVP) followed through the PEM and base64 layers: EVP_ENCODE_CTX has been opaque since OpenSSL 1.1.0 and is always allocated by EVP_ENCODE_CTX_new(), so clearing it on free covers PEM reading, PEM writing and BIO_f_base64.
How it was found
The same freed-block measurement program, run over PEM encoding of private keys.
Fix
Clear the context in EVP_ENCODE_CTX_free(). test_encode_ctx_free_clears_input leaves a partial block in a context, swaps the free function and fails if the freed context still holds the input.

oqs-provider — Clear private key copies before freeing themAwaiting CI approval · draft

open-quantum-safe/oqs-provider #861 · submitted 2026-10-29
Problem
When post-quantum private keys were encoded to or decoded from PKCS#8 DER, and when they were exported, oqs-provider freed temporary copies of the key without clearing them. ML-KEM, ML-DSA and the other post-quantum private keys stayed in released heap memory.
Background
How keys travel through an OpenSSL 3 provider, and the zeroisation rule of ISO/IEC 19790 (FIPS 140-3, KCMVP). OSSL_PARAM_free() clears only secure-heap blocks, which is why OpenSSL's own ml_kem_export() cleanses its parameters before freeing them; oqs-provider had no such step.
How it was found
The freed-block measurement program run over 111 algorithms: 1,377 freed blocks held private keys. The fix removes every one on oqs-provider's own paths (55 signature algorithms × 8 paths); the 823 left come from libcrypto. A second run over the key-exchange paths found the export copy for all 56 KEM algorithms.
Fix
ASN1_STRING_clear_free() and OPENSSL_clear_free() in the encoder and decoder, and OPENSSL_cleanse() of the exported parameters before OSSL_PARAM_free(). A new test, oqs_privkey_cleanse, watches freed blocks and fails if any of the changes is reverted.

liboqs — Let ML-DSA Wycheproof verify vectors reach the library with wrong lengthsAwaiting CI approval · draft

open-quantum-safe/liboqs #2665 · submitted 2026-10-31
Problem
liboqs's test harness rejected ML-DSA signatures of the wrong length, and contexts longer than 255 bytes, before calling the library, and the runner counted that as a pass. The Wycheproof IncorrectSignatureLength and InvalidContext vectors never reached liboqs: disabling the signature-length check in liboqs's ML-DSA glue code left every test passing.
Background
FIPS 204 fixes the ML-DSA signature length for each parameter set. liboqs wraps the mldsa-native implementation in its own glue code, and that glue is what has to enforce the length at the public API.
How it was found
A sweep of the Wycheproof test harnesses of nine cryptography libraries for vectors that are skipped, followed by mutation testing on liboqs.
Fix
For ML-DSA, reject only malformed hex input, as the neighbouring SLH-DSA branch already does, so the vectors exercise the library's own checks. Disabling the glue check now fails the Wycheproof tests for all three parameter sets.
