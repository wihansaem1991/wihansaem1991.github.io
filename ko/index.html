OpenSSL — kdf_pbkdf1_derive_skey()에서 PBKDF1 파생 키를 지우고 해제승인

openssl/openssl #33444 · 제출 2026-10-29 · 승인 2026-10-30 · master, 3.6, 4.0, 4.1
문제
파생 키를 EVP_SKEY로 가져온 뒤 임시 버퍼를 OPENSSL_free()로 해제해서, 키 전체가 해제된 힙 메모리에 그대로 남았습니다.
배경 지식
FIPS 140-3와 KCMVP 검증의 바탕인 ISO/IEC 19790은 다 쓴 키를 지우도록(제로화) 요구합니다. 파생 키도 비밀값이라 메모리를 돌려주기 전에 지워야 하고, OpenSSL은 이를 위해 OPENSSL_clear_free()를 둡니다.
찾은 방법
OpenSSL 할당자를 바꿔 해제되는 블록마다 키 바이트가 남았는지 재는 측정 프로그램으로 찾았습니다. pbkdf1.c:318에서 해제되는 20바이트 블록에 키 전체가 들어 있었습니다.
수정
두 경로 모두 OPENSSL_clear_free()로 바꿨습니다. 기존 시험 test_kdf_pbkdf1_skey가 이제 해제 블록을 감시하고, 수정을 되돌리면 실패합니다.
리뷰
리뷰어 두 명이 승인했고, FIPS와 관련된 버그로 분류됐습니다.
증빙

pkcs11-provider — 큰 버퍼에도 ECDH 공유 비밀값만 돌려주기수정 반영, 재리뷰 대기

openssl-projects/pkcs11-provider #813 · 제출 2026-10-30
문제
PKCS#11 토큰을 쓰면 EVP_PKEY_derive()가 공유 비밀값 크기가 아니라 호출자 버퍼 크기만큼 토큰에 요청했습니다. NSS softokn은 P-256 비밀값 앞을 0으로 채워 돌려줘서, 64바이트 버퍼에는 0 32개 뒤에 비밀값이 들어갔고 ECDH 양쪽 값이 서로 달라졌습니다.
배경 지식
PKCS#11·HSM 연동 지식이 필요했습니다. ECDH 파생(CKM_ECDH1_DERIVE, CKD_NULL)은 출력 길이를 키 템플릿의 CKA_VALUE_LEN에서 가져오고, OpenSSL EVP_PKEY_derive()는 길이를 버퍼 크기로 받아 실제로 쓴 바이트 수를 돌려줍니다. 두 규약이 어긋나는 지점이었습니다.
찾은 방법
차등 시험으로 찾았습니다. 같은 ECDH 파생을 OpenSSL 기본 provider와 NSS softokn 토큰 위의 pkcs11-provider에 여러 크기의 출력 버퍼로 넣어 결과를 비교했습니다.
수정
요청 길이를 키 크기로 제한했습니다. 새 회귀 시험이 오래된 누수도 드러냈습니다. 한 문맥에서 두 번 파생하면 상대 공개점 사본을 덮어써 앞 사본이 새는 문제로, Address Sanitizer 시험이 잡았고 같은 PR에서 고쳤습니다.
리뷰
메인테이너가 승인한 뒤 회귀 시험 구조 정리와 Address Sanitizer 실패 해결을 요청했고, 두 가지 모두 새 커밋으로 반영했습니다.

문제
Mbed TLS는 자기가 해석하는 확장이 인증서에 두 번 나오면 거부했지만, 건너뛰거나 콜백에 넘기는 확장이 두 번 나오면 그대로 받아들였습니다.
배경 지식
RFC 5280 4.2절은 인증서에 같은 확장을 두 번 넣지 못하게 합니다. 건너뛰는 확장은 해석하지 않으니, 이 규칙을 적용하려면 확장 목록의 DER 구조를 직접 다뤄야 했습니다.

수정

문제
--set confdir=...을 주면 mitmproxy가 그 폴더의 config.yaml에서 cert_passphrase를 읽기 전에 CA부터 불러왔습니다. 그래서 암호가 걸린 CA 키를 읽지 못해 시작하자마자 종료됐습니다(2023년부터 열린 이슈 #6014).
배경 지식
TLS 가로채기 구조를 알아야 했습니다. mitmproxy는 자체 CA로 인증서를 즉석에서 서명하므로 시작할 때 CA 개인키를 읽어야 하고, 암호화된 PKCS#8 키는 암호가 먼저 있어야 합니다. 옵션 관리자는 갱신할 때마다 애드온에 알리므로, 갱신 순서가 애드온이 보는 값을 정합니다.
찾은 방법
메인테이너가 원인을 짚어 둔 이슈 #6014와, 2023년 이후 리뷰 없이 멈춘 PR을 보고 골랐습니다. 암호 걸린 CA로 리눅스에서 재현했습니다.
수정
--set 옵션과 설정 파일을 옵션 사본(구독자가 없음)에서 먼저 합친 뒤 결과를 한 번에 적용합니다. 우선순위는 그대로입니다. 새 시험은 암호 걸린 CA로 mitmdump를 띄우고, 예전 순서로 되돌리면 실패합니다.

문제
key_to_type_specific_der_bio()가 키의 i2d 함수가 만든 DER를 OPENSSL_free()로 해제했습니다. 개인키라면 이 버퍼에 키 전체가 들어 있어서, RSA·EC·DSA·SM2 키를 i2d_PrivateKey()나 "type-specific" DER로 인코딩할 때마다 키가 해제된 메모리에 남았습니다. PEM 경로는 이미 사본을 지우고 있었습니다.

OpenSSL — EVP_ENCODE_CTX를 해제할 때 지우기CI 실행 허가 대기

openssl/openssl #33430 · 제출 2026-10-28
문제
base64 문맥은 입력의 마지막 부분 줄을 들고 있는데, 지우지 않고 해제했습니다. PEM_write_bio()는 개인키 DER를 이 문맥으로 인코딩하므로 키의 마지막 (길이 mod 48)바이트가 해제된 메모리에 남았습니다. RSA라면 iqmp 끝부분, Ed448·ML-DSA·ML-KEM이라면 개인키 바이트입니다. PEM을 읽을 때도 base64 문자열이 같은 식으로 남았습니다.
배경 지식
제로화 요건(ISO/IEC 19790, FIPS 140-3·KCMVP)을 PEM·base64 계층까지 따라갔습니다. EVP_ENCODE_CTX는 OpenSSL 1.1.0부터 불투명 구조체라 항상 EVP_ENCODE_CTX_new()로 만들어지므로, 해제할 때 지우면 PEM 읽기·쓰기와 BIO_f_base64가 모두 해결됩니다.
찾은 방법
같은 해제 블록 측정 프로그램을 개인키 PEM 인코딩에 돌려 찾았습니다.
수정
EVP_ENCODE_CTX_free()에서 문맥을 지웁니다. 새 시험 test_encode_ctx_free_clears_input은 문맥에 부분 블록을 남긴 채 해제 함수를 바꿔 끼우고, 해제된 문맥에 입력이 남아 있으면 실패합니다.

oqs-provider — 개인키 사본을 지운 뒤 해제CI 실행 허가 대기 · 초안

open-quantum-safe/oqs-provider #861 · 제출 2026-10-29
문제
양자내성 개인키를 PKCS#8 DER로 인코딩·디코딩하거나 내보낼(export) 때, oqs-provider가 키의 임시 사본을 지우지 않고 해제했습니다. ML-KEM·ML-DSA를 비롯한 양자내성 개인키가 해제된 힙 메모리에 남았습니다.
배경 지식
OpenSSL 3 provider 안에서 키가 오가는 경로와 ISO/IEC 19790(FIPS 140-3·KCMVP)의 제로화 요건을 알아야 보이는 문제였습니다. OSSL_PARAM_free()는 보안 힙 블록만 지웁니다. 그래서 OpenSSL의 ml_kem_export()는 해제 전에 파라미터를 지우는데, oqs-provider에는 이 단계가 없었습니다.
찾은 방법
해제 블록 측정 프로그램을 알고리즘 111종에 돌렸습니다. 개인키가 든 해제 블록이 1,377개였고, 수정 뒤 oqs-provider 자체 경로(서명 55종 × 8개 경로)에서는 0개가 됐습니다. 남은 823개는 libcrypto 몫입니다. 키 교환 경로를 다시 재서 KEM 56종 전부에서 내보내기 사본을 찾았습니다.
수정
인코더·디코더는 ASN1_STRING_clear_free()·OPENSSL_clear_free()로 바꾸고, 내보낸 파라미터는 OSSL_PARAM_free() 전에 OPENSSL_cleanse()로 지웁니다. 새 시험 oqs_privkey_cleanse가 해제 블록을 감시하고, 수정을 하나라도 되돌리면 실패합니다.

liboqs — 잘못된 길이의 ML-DSA Wycheproof 검증 벡터가 라이브러리까지 가도록CI 실행 허가 대기 · 초안

open-quantum-safe/liboqs #2665 · 제출 2026-10-31
문제
liboqs 시험 하네스가 길이가 틀린 ML-DSA 서명과 255바이트를 넘는 context를 라이브러리 호출 전에 걸렀고, 실행기는 이를 통과로 셌습니다. 그래서 Wycheproof IncorrectSignatureLength·InvalidContext 벡터가 liboqs에 닿지 않았고, liboqs ML-DSA 연결 코드의 서명 길이 검사를 꺼도 시험이 전부 통과했습니다.
배경 지식
FIPS 204는 ML-DSA 매개변수 집합마다 서명 길이를 고정합니다. liboqs는 mldsa-native 구현을 자체 연결 코드로 감싸므로, 공개 API에서 이 길이를 지키는 책임이 그 연결 코드에 있습니다.
찾은 방법
암호 라이브러리 9곳의 Wycheproof 시험 하네스에서 건너뛰는 벡터를 훑은 뒤, liboqs에서 변이 시험으로 확인했습니다.
수정
ML-DSA도 바로 옆 SLH-DSA 분기처럼 잘못된 hex 입력만 거르고 나머지는 라이브러리로 넘깁니다. 이제 연결 코드의 길이 검사를 끄면 세 매개변수 집합 모두 Wycheproof 시험이 실패합니다.
